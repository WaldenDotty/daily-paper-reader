## 摘要
低推力轨迹优化是深空任务设计的核心技术。基于庞特里亚金极小值原理（PMP）的间接方法提供了严格的优性保证，但其实际应用面临三大瓶颈：（1）横截条件必须针对每种约束类型逐例推导；（2）不同动力学模型需要重复编写代码；（3）打靶方程对初值猜测高度敏感。本文提出了HELIOS（低推力行星际优化系统启发式引擎），一种围绕大语言模型（LLM）构建的轨迹优化代理。给定自然语言描述的物理问题，系统自主执行PMP符号推导、SymPy验证、C++打靶代码生成和数值求解，无需人工干预。关键创新包括：（1）一种约束自适应推导框架，将任意约束统一为psi(x,p)=0形式，并自动生成自由参数（如引力辅助转弯角）的平稳性条件；（2）动力学自适应的四模块代码生成，支持非标准动力学（太阳帆、J2摄动）而无需修改底层模板；（3）覆盖PMP推导中关键易错点的通用推导规则集。在11个渐进式测试场景上的实验表明，HELIOS能正确推导并求解从简单交会（8个变量）到多段停留转移（48个变量）、引力辅助轨迹（17个变量）和太阳帆最短时间转移（8个变量）的问题。最佳编译成功率可达100%（11/11）。多模型比较（8个开源LLM后端，总分250-905）验证了模型无关架构，并揭示了模型规模与推导能力之间的正相关性。

## Abstract
Low-thrust trajectory optimization is a core technology in deep-space mission design. Indirect methods based on Pontryagin's Minimum Principle (PMP) offer rigorous optimality guarantees, yet their practical application faces three bottlenecks: (1) transversality conditions must be derived case by case for each constraint type; (2) different dynamics models require repeated code rewrites; and (3) shooting equations are highly sensitive to initial guesses. This paper presents HELIOS (Heuristic Engine for Low-thrust Interplanetary Optimization System), a trajectory optimization agent built around a large language model (LLM). Given a physical problem described in natural language, the system autonomously performs PMP symbolic derivation, SymPy verification, C++ shooting-code generation, and numerical solution without human intervention. Key innovations include: (1) a constraint-adaptive derivation framework that unifies arbitrary constraints into psi(x,p)=0 form and automatically generates stationarity conditions for free parameters (e.g., gravity-assist turning angle); (2) dynamics-adaptive four-module code generation supporting non-standard dynamics (solar sail, J2 perturbation) without modifying the underlying template; and (3) a general derivation rule set covering critical error-prone points in PMP derivation. Experiments on 11 progressive test scenarios show that HELIOS correctly derives and solves problems from simple rendezvous (8 variables) to multi-leg stay transfers (48 variables), gravity-assist trajectories (17 variables), and solar-sail minimum-time transfers (8 variables). The best compilation success rate reaches 100% (11/11). A multi-model comparison (8 open-source LLM backends, total scores 250-905) verifies the model-agnostic architecture and reveals a positive correlation between model scale and derivation capability.

### 2. 论文提出的方法论

#### 核心思想

HELIOS采用**五阶段流水线架构**，核心设计原则是：问题描述中只陈述物理事实，不含任何PMP推导结果；LLM从极小值原理的原始形式出发，自主完成全部推导与代码生成。

```
用户自然语言描述 → Stage 1约束解析(结构化JSON) → Stage 2 PMP推导
→ Stage 3 SymPy符号验证(失败最多3轮精化) → Stage 4 C++代码生成
→ Stage 5编译+同伦求解 → 输出轨迹/质量/收敛报告
```

#### 关键技术创新

**（1）约束自适应统一推导框架（核心创新）**

- 将所有约束统一为 **ψ(x, p) = 0** 形式，其中x为状态变量、p为耦合在约束中的自由参数；
- 三条核心处理规则：
  - **Rule B**（内点约束）：每个内点约束ψ引入乘子ν，协态在t_k处跳跃：**λ⁺(t_k) = λ⁻(t_k) + νᵀ∂ψ/∂x**，ν作为打靶变量加入；
  - **Rule B2**（约束参数）：自动扫描约束表达式，识别既非状态也非乘子的自由参数p（如引力辅助的转弯角δ、方位角φ），为其生成平稳性方程 **Σₖ νₖ∂ψₖ/∂p = 0**；
  - **自由时间**：每个自由时间t_k生成横截条件 **H(tₖ⁻) − H(tₖ⁺) − Σν∂ψ/∂tₖ = 0**；
- 彻底打破了传统上必须针对每种约束类型单独推导横截条件的限制。

**（2）动力学自适应四模块代码生成（核心创新）**

- **DYNAMICS/SWITCH/RESIDUAL/SOLVE** 四模块分离架构：
  - 标准低推力问题（化学/电推进、bang-bang控制）仅需生成RESIDUAL和SOLVE两个模块，DYNAMICS和SWITCH使用模板默认；
  - 非标准动力学（太阳帆、J2摄动）则四个模块全部由LLM生成，包括右端函数、最优锥角控制律、传播逻辑；
- 模板固定部分包含归一化常数初始化、轨道力学、RK4积分器、自适应ε-同伦求解器及MINPACK hybrd1接口；
- 星历支持两种模式：开普勒根数传播（eph[0]≥0）与固定笛卡尔状态直接赋值（eph[0]==-1）。

**（3）通用推导规则集**

| 规则 | 内容 | 目的 |
|------|------|------|
| Rule G1 | λ₀必须作为打靶变量并纳入球面归一化 | 处理异常乘子 |
| Rule G2 | 最优控制方向必须验证H的极大/极小 | 避免符号混乱 |
| Rule G3 | 控制方向依赖状态时必须包含几何导数项∂n/∂x | 包络定理只消去∂H/∂α |
| Rule G4 | 不出现在动力学中的变量（如太阳帆质量）不得作为状态 | 保持状态维度一致 |
| Rule G5-G6 | 禁止占位符与化简，J2需要完整3×3 Jacobian | 保证推导完整性 |

**（4）数值稳定性策略**

- 无量纲化（AU/年/归一化单位）；时间变量以分数τ∈[0,1]存储，避免MJD绝对量级与协变量不匹配；目标天体在实际到达历元求值；残差仅用原始归一化差异；明确声明H符号约定（极小值原理形式）。

### 8. 不足与局限

1. **数值收敛依赖随机初值**：17+变量场景（如S10引力辅助）随机重启动策略在时限内常无法收敛。作者明确承认d4维度带偶然性，收敛分数需要谨慎解读。缺少物理启发初值构建、降阶问题延拓、近似解热启动等系统化初始化研究——这是当前最大弱点；
2. **SymPy验证覆盖不全**：对复杂动力学模型（太阳帆），符号验证因表达式爆炸而超时，此时只能跳过验证、直接依赖LLM推导的正确性，可靠性保障机制出现空档；
3. **LLM输出不确定性**：同问题两次推理可能产生风格不同的代码，论文未提供确定性后处理方案（仅建议"推荐"检查打靶方程线性无关性）；
4. **多模型对比的公平性局限**：仅一次运行、未报告方差；收敛维度随机性导致总分波动可能影响排名可靠性；未包含闭源前沿模型对比；
5. **实验场景来源集中**：所有场景（除S10、S11外）主要来自作者本人此前发表的论文（[21][22][23]），独立第三方基准验证欠缺，存在潜在的评估偏差风险；
6. **评估指标分层偏重pipeline达成而非物理最优性**：编译/推导占70%分数，实际收敛与精度仅占30%，可能高估了系统在真正困难问题上的能力；
7. **无效率对比数据**：未与传统人工推导、现有间接法软件工具进行时间/人力成本对比，自动化增益缺乏定量证据。
